# שיעור 5 — תשובות

## חלק א — מפת ה-cluster

| רכיב | איפה הוא רץ (הנהלה / כל node) | מה הוא עושה, במשפט אחד | אנלוגיה |
|---|---|---|---|
| API server | הנהלה | הכניסה היחידה ל-cluster: מקבל כל בקשה מ-kubectl, בודק שהיא תקינה ושמותר, ושאר הרכיבים מדברים דרכו | הקופאית שרושמת כל הזמנה לפני שהיא עוברת למטבח |
| etcd | הנהלה | מסד הנתונים של ה-cluster עצמו: שומר מה צריך להיות ומה יש (לא נתוני האפליקציה), ואם הוא נמחק ה-cluster מאבד את הזיכרון שלו | פנקס ההזמנות של הקונדיטוריה, שרשום בו מה הוזמן ומה יש בוויטרינה |
| scheduler | הנהלה | מחליט על איזה node ירוץ כל pod חדש, לפי מקום פנוי, ורק משבץ ולא מריץ בעצמו | מי שמחלקת את ההזמנות החדשות לתחנות העבודה במטבח לפי מי שפנויה |
| controller manager | הנהלה | לולאת הבקרה: משווה כל הזמן בין המצב הרצוי למצב בפועל, ומתקן (למשל יוצר pod חדש כשחסר) | המפקחת שבודקת שיש בוויטרינה את מספר העוגות שנקבע, ומבקשת להוסיף כשחסר |
| kubelet | כל node | הנציג של ה-node: שואל "מה שובץ אליי?", מפעיל את ה-containers, מרים מחדש container שקרס, ומדווח כל כמה שניות שה-node חי | אחראית המשמרת בתחנת העבודה, שמכינה את מה ששובץ לה ומדווחת למוקד |
| container runtime | כל node | התוכנה שמריצה בפועל את ה-containers מה-images, לפי ההוראות של ה-kubelet | הטבח שמכין בפועל את העוגה לפי המתכון, כשאחראית המשמרת אומרת לו מה להכין |
| kube-proxy | כל node | דואג שבקשה לשם של Service תגיע לאחד ה-pods הנכונים שמאחוריו | השליחה שלוקחת הזמנה שהגיעה לכתובת של העסק ומוסרת אותה לתחנה הנכונה |
| coredns | רץ כ-pod רגיל ב-kube-system, על ה-nodes | שרת ה-DNS של ה-cluster: מתרגם שם של Service (כמו `greeter`) לכתובת שלו, כמו שברשת של Compose פונים ל-container לפי שם | ספר הטלפונים של הקונדיטוריה, שבו מחפשים שם של תחנה ומקבלים את המספר שלה |

## חלק ב — תרחישים

### 1. scale

הפקודה `kubectl scale` נשלחת ל-API server, שבודק אותה ושומר ב-etcd שהמצב הרצוי הוא 4 replicas. ה-controller manager רואה שיש 2 pods מתוך 4 רצויים, ויוצר 2 pods חדשים. ה-scheduler בוחר לכל pod חדש על איזה node ירוץ. ה-kubelet באותו node רואה שמשהו שובץ אליו ומפעיל אותו דרך ה-container runtime, ומדווח ל-API server שה-pod במצב Running.


### 2. שלוש בלילה

ה-kubelet שב-node מזהה שה-container קרס ומרים אותו מחדש, באותו pod, בלי שאף אחד יתערב. אם מישהי הייתה מוחקת את ה-pod כולו, ה-controller manager היה רואה שיש פחות pods מהרצוי ויוצר pod חדש, וה-scheduler היה משבץ אותו ל-node. בשני המקרים המערכת מתקנת את עצמה כי המצב הרצוי נשמר ב-etcd.


### 3. node נכבה

ה-kubelet ב-node 2 מפסיק לדווח, וההנהלה מסמנת את ה-node כ-NotReady. ה-controller manager רואה שה-pods שרצו עליו אבדו ויוצר במקומם pods חדשים, וה-scheduler משבץ אותם ל-nodes 1 ו-3. ב-cluster של Docker Desktop יש node אחד בלבד, שגם מכיל את ההנהלה. אם המחשב נכבה, הכל נעצר, כולל ה-cluster עצמו, ואין node אחר שיריץ את ה-pods. כשהמחשב נדלק והמערכת חוזרת, המצב הרצוי עדיין שמור ב-etcd וה-pods נוצרים מחדש.


### 4. מהכיתה לענן

`imagePullPolicy: Never` לא יעבוד, כי ה-images בנויים רק על המחשב המקומי, וב-nodes של EKS אין אותם. ה-pods ייכשלו עם `ErrImageNeverPull`. צריך לדחוף את ה-images ל-registry (למשל ECR של AWS), לכתוב ב-`image:` את הכתובת המלאה שלהם, ולשנות את ה-pull policy ל-`IfNotPresent` או להסיר אותה. גם Service מסוג `NodePort` לא מתאים: הוא פותח פורט על ה-nodes, שבענן הם מכונות שלא חשופות לאינטרנט כברירת מחדל. צריך להחליף ל-`LoadBalancer`, או להשתמש ב-Ingress.


### 5. pod בודד

pod שנוצר עם `kubectl run` הוא pod בודד, ואין שום רכיב שאחראי לשמור שיהיה כזה. כשמוחקים אותו, ה-controller manager לא יודע שהיה צריך להיות כזה, ולכן הוא לא חוזר. ה-pods של `web` שייכים ל-Deployment שמגדיר מצב רצוי של מספר replicas, ולכן ה-controller manager יוצר pod חדש כשאחד נמחק. כדי ש-stats יחזור תמיד, הייתי יוצרת לו Deployment עם `replicas: 1` במקום pod בודד.
